## Findings (verified live as a guest)

**P1 #1: Truncated files get a wrong report in both directions.** Truncation is the case the page, FAQ and guide lead with.
- **Over-claim (T01):** a file cut after page 3's content: "Recovered 5 pages", "Rebuilt the cross-reference table; added the missing end-of-file marker". Pages 4–5 come out **blank** in PDFium, pdf.js and MuPDF (render-T01-fdp.png). `qpdf --check` on the output gives 93 warnings: content stream 34 is a stub.
  - **Cause:** the lenient pdf-lib load finds 5 page dicts (they come before the content streams) and returns `partial:false, totalPages:null`. The cut-off check only exists in the scan path.
  - **Promises broken:** the page says "The tool flags the file as cut off in that case", "a page survives only if every part it needs is present", and the FAQ says "rather than a broken or incomplete download that looks like it worked but didn't".
  - Someone will delete the original on that message.
- **Under-claim (T04):** a qpdf-ordered copy cut at 70 % (p1–p2 complete, p3 partial): "This file couldn't be recovered — no complete page could be found in it". qpdf and mutool both output 5 pages with p1–p2 (and part of p3) readable (render-T04-mutool.png). Cause not confirmed (code only: the scan path's reachability walk or the lenient load). Same in Firefox.
- **Fix direction:**
  - after the lenient load, check every page's /Contents (and the resources it uses) is a real stream and not past the last `endobj`;
  - when any is missing, take the scan path's verdict ("Recovered 3 of 5 pages — cut off") or drop/flag blank pages;
  - make the scan path keep a page whose own objects are complete even when siblings in the tree are missing.

**P1 #2: "No structural damage was found" on a broken page tree, and the output is still broken.**
- **P01** (Kids [5 7 **99** 20 21], obj 99 missing; page object 19 intact): "No structural damage was found; the file was rewritten as a clean copy (4 pages)".
- The output keeps the dangling Kid:
  - **Chrome's PDFium fails to load page 3** (render-P01-fdp.png);
  - pdf.js reports 3 pages and errors on page 3;
  - MuPDF shows 5 pages with page 3 blank.
- The form page (p3) is lost although its object is in the file. The scan path would have found it, as it did on P02.
- qpdf produces a clean 4-page file (render-P01-qpdf.png).
- **Fix direction:** after the lenient load, walk the page tree. If a Kid is missing or not a Page/Pages dict, say so, rebuild Kids from the valid pages (or run the scan path) and report "rebuilt the page list".

**P2 #3: An interrupted save is applied as if it had been saved (I02).**
- The update objects were written but the save never finished (no xref/trailer).
- Every viewer, qpdf and mutool show the last saved version: 5 original pages.
- FDP's lenient parser takes the **newest copy of each object**, so the output has page 1 replaced by the unsaved text and page 5 removed. It says "No structural damage was found".
- The user gets a document no other program shows them, and loses a page. I03 (bad /Prev) also says "No structural damage" (the content matches viewers there).
- **Suggest:** detect objects after the last %%EOF/startxref, report "an unfinished save was found", and offer the last saved version, or ask (Q3).

**P2 #4: Encrypted file without its trailer: "Recovered 5 pages" with every page blank (E02).**
- The /Encrypt reference went with the trailer, so `ignoreEncryption` copies ciphertext.
- Five blank pages. The form value is ciphertext (render-E02-fdp.png).
- Baselines can't decrypt it either, but qpdf reports errors.
- **Suggest:** if any stream fails to inflate, or an /Encrypt dict exists but isn't referenced, say "this file is encrypted and its key information is damaged; the content can't be recovered".

**P2 #5: Junk over 1 KB before the header is rejected as "not a PDF" (J02, 2048 bytes).**
- Message: "This file isn't a PDF, and we couldn't tell what kind of file it is … use a converter such as Word to PDF".
- pdf.js, MuPDF, qpdf and mutool all recover 5/5. Mail gateways and bad transfers can prepend more than 1 KB.
- **Suggest:** if `%PDF-` occurs anywhere in the first ~64 KB (and `%%EOF`/`obj` appear later), treat it as junk-before-header.

**P2 #6: Failure fallbacks loop back.**
- On a file Repair can't save (T03, T04), the page offers "Try PDF to Word →" and "Try PDF to JPG →".
- PDF to Word shows `"…" can't be read — it looks damaged · Try the Repair PDF tool`, which sends the user back.
- PDF to JPG says "This file couldn't be read as a PDF … It may be damaged".
- The FAQ and guide present these as salvage routes.
- **Suggest:**
  - let PDF to Word / JPG skip the damaged-file gate when arriving from Repair, so they try their own parser;
  - or offer something that differs, e.g. "extract text from the raw bytes" (FlateDecode streams can be inflated and shown even with no complete page);
  - or say honestly that nothing on the site can read it.

**P2 #7: Other tools' "Repair PDF" button loses the language and the file. Some tools have no button.**
- The toast action is `window.location.assign("/tool/repair-pdf")`. From /es/tool/merge-pdf, /de/tool/compress-pdf and /fr/tool/pdf-to-word it lands on the English page; those locale pages have a translated H1 ("Reparar PDF", "PDF Reparieren", "Réparer PDF").
- The user must find and drop the file again.
- Rotate PDF and PDF to JPG say the file may be damaged but give no Repair link.
- **Suggest:** use `localizedHref`; pass the file (same-tab state or IndexedDB hand-off); use one shared damaged-file message with the action everywhere.

**P3 #8: Message precision.**
- E01/E03: after the drop zone's unlock step, the file is already rewritten, so "No structural damage was found" hides that it was damaged. Say "Unlocked and rebuilt".
- O01: "Recovered 2 pages" doesn't say the original count couldn't be read.
- Not-PDF messages always suggest "Word to PDF", even for a JPEG (→ Image to PDF) or HTML (→ HTML to PDF).
- Keyboard: after a failure, focus drops to BODY. The polite live region does announce the message.

**P3 #9: Privacy wording.**
- "Nothing is requested from any other server, no helper download happens" is not exact. Attempt Repair downloads `pdfRecover` and `repairDiagnose` code from freedailypro.com and calls `auth.me,cloudStorage.config`, and Google Analytics/ads stay active.
- No file data leaves the page (verified).
- **Suggest:** "Your file is never sent anywhere; the page only loads its own code."

**P3 #10: Document info dropped when the trailer is lost.** On X03, X04, T01 and P02 the output has no Title/Author. qpdf also loses it; mutool finds the Info dict by scanning. Scan path: outline dropped (documented).

**P3 #11: Content, SEO, video.**

- The FAQ has two near-duplicate pairs ("What kinds of PDF damage does this actually fix?" / "What kinds of damage can it fix?"; "Will the repaired file look exactly the same…" / "…match the original exactly?"). It also contradicts itself on truncated downloads.
- The guide's "Recovered 9 of 14 pages" example isn't what a typical cut file gets (P1 #1).
