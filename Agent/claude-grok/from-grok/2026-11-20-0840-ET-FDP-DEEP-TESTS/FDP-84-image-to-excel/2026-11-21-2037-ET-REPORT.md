## How to work with us

**Owner context (Santosh's standing rulings):** charging per page load is a P1. A real save at 0 trial uses is a P1. A full result merely *visible* at 0 uses is an owner question, not a P1.

**P0:** none.

**P1 — per-page-load charging (1):**
- One trial use buys unlimited downloads until the page is reloaded.
  - Measured on the live site with the `usage.log` POSTs counted:
    - X02: first download 0→1 (1 POST).
    - X03 the same file again, X04 after editing a cell, X05 after reading a **different** picture: all downloaded, 0 POSTs.
    - X08: reload, then download 1→2.
    - One-load runs: 16 .xlsx from 9 different pictures for 1 use (`casesdl`), 5 for 1 (`casesdl-b`), 2 for 1 (`casesdl-c`).
  - **Where to look:** the per-export key logic exists: `dI(e,t)` → free / again / first in `index-xgcQ0Xo8.js`, exposed as `tryUseExport(key)` / `logExportNow(key)` by the `la()` hook in `ToolPage-DrleSM7T.js`. But the DownloadButton (`ql`) still calls `logUsageNow` → `tryUse` → `xI`, which sets a per-tool flag (`Kt`) that is cleared only when the page unmounts (`wI`). So the key logic is never reached from this tool (excerpt: evidence/js/ToolPage-gate-excerpt.js).
  - **Intent:** one use = one spreadsheet. A new picture, or an edited table, should be a new use. Re-downloading the same unchanged file can stay free.

**Owner question (not a P1 under the current rule):**
- At 0 uses the whole result is still produced and shown as an editable grid: every cell, which is exactly what goes into the .xlsx (zero.json X01).
  - Download, Save to Google Drive, and download after reload all show the cap dialog with 0 POSTs, so no save leaks.
  - A user can still read or retype the figures from the grid. Santosh to rule on whether the grid should be blurred or limited at 0.

**P2 — where to look:**
1. **German thousands become decimals: "1.200" → 1.2, even with German selected.**
   - In the same table "1.234,50 €" → 1234.5 and "1.099,00 €" → 1099 are right. But "Menge 1.200" is written as **1.2** with number format `0.000`, so Excel *shows* "1.200" while SUM uses 1.2. That is a silent 1000× error.
   - The same happens with English selected (casesdl-c-0 vs -1).
   - Look at the number parser in `tablesToExcel`. A dot followed by exactly three digits, in a column or document that uses comma decimals (or when German is chosen), is a thousands separator. Where it is ambiguous, keep the cell as text and add a note rather than guessing.
2. **A tilted photo on a dark background produces wrong data, and Straighten does nothing.**
   - `tilt.jpg`: a 6° page with dark corners, like a phone photo on a desk. The table came back as 2 columns (Item + Date). The dates were shifted up two rows (the heading row got Stapler's date, "Paper A4" got Toner's 2026-03-09), and 5 columns were lost, all at "about 90% confidence".
   - **Where to look:** the deskew `v()` in `scanRun` projects dark pixels over ±8°. Dark corners dominate the projection, so the estimated angle is wrong.
   - The same page on a light background (`tilt-light3/6.jpg`) straightens correctly. Suggestions: limit the projection to the page area (e.g. ignore borders or near-black fill), and flag shifted rows (row-count mismatch per column) instead of offsetting values.
3. **No video and no blog/guide** for this tool (/blog/image-to-excel 404). It's a strong use case: "photo of a table to Excel" is a common search, and "will my numbers be real numbers?" is answered best by showing it.
4. **Inbound handoff from Document Scanner still 404s (re-confirmed; first filed in FDP-61).**
   - Document Scanner → "Edit as Excel" navigates to `/tools/image-to-excel` (plural) → "Hmm, we couldn't find that page" (handoff.json, X10).
   - The code is ``Ce(`/tools/${t}`)`` after storing files under the `scan-convert` handoff key, which ScanConverter reads, so only the path is wrong.
5. **Locale pages are partly in English.** All 10 hreflang pages keep the English `<title>` and meta description. The /de and /ja pages also keep "About …", "How to use it", "Common questions", "Details…" and "Take photo with camera" in English.

**P3:**
- 6° light tilt *without* Straighten: "$0.85" read as **40.85**, written as the number 40.85 (91% confidence). It's correct with Straighten, so consider suggesting Straighten when a tilt is detected.
- Small picture (48–62% confidence) still writes misreads as numbers ("$4.50" → 5450, dates "20260301"). Below about 70% confidence, consider leaving numbers as text or warning more strongly.
- Low-contrast picture: "12" → "iz" in one run (it was right in another). Boost contrast made no difference.
- Corrupt JPEG: "The source image could not be decoded.. Try a clearer picture." has a double period, and it took **122 s** to appear.
- Copy:

  - "in this order they become the page" doesn't fit a spreadsheet.

- Layout: iPhone SE overflows by 9 px (a header button); ja desktop by 3 px. Axe: desktop `label-content-name-mismatch` (.right-2) + `region`; Pixel 7 color-contrast on the ad label (sitewide).

## Intent

Someone photographs a printed price list or statement and wants figures they can SUM. The tool is honest and careful: it shows every cell before download, keeps codes as text, writes real dates and currency, and explains its limits. The two P2 data issues matter because the output *looks* right (1.200 displays as 1.200; shifted dates are valid dates) while the totals are wrong. That's exactly the failure a user won't notice. The P1 is the same per-load gate seen on earlier tools: the export-key code (`logExportNow`) exists but this button doesn't use it.
