## P1 (2 items)

1. **Per-page-load charging** (same root cause as #84–#88).
   - **Measured (`left.json`, `left2.json`, `charge-2.json`):**
     - Placing fields and a failed build are free; the use is taken at the first successful Download of a page load (1 `usage.log` POST, server `usageToday` 0→1).
     - In load 1, **13 different fillable PDFs** were downloaded (blank forms, an existing form, a rotated page, a 35-page file, A4…) with **1 POST** in total.
     - Reload + download: 1→2. Next load: cap dialog, 0 POSTs, no file.
   - Note: in the very first run the badge jumped 0/2→2/2 on one POST. The server responses in `charge-2.json` and `left2.json` show 0→1 per load, so I treat that jump as pooled-device noise, not a double charge.
   - **Intent:** one use = one created form.
2. **Multi-line fields get a 69 pt font, so answers beyond the first word or two can't be seen or printed.**
   - pdf-lib's auto-size is baked into each field's `/DA` from the box height: multi-line 260×80 → `/Helvetica 69 Tf`; text box 180×22 → `/Helvetica 17 Tf`. Readers obey a fixed DA size.
   - pdf.js shows the textarea at 77.9 px; "राम कुमार / Second line of notes / Third line" shows only "राम कुमार" (screens `pdfjs-saved-L01-render`).
   - **End to end on this site:** filled in Fillable Forms with 3 lines → the field shows only "Line" (`FF-filled-mupdf-vs-pdfium`); then Flatten PDF → the final document's text layer for Notes is just "Line" (`flatten-crosscheck.json`).
   - Text boxes at 17 pt hold about 18 characters in the default 180 pt width, so a normal address scrolls out of view and prints cut off.
   - **Why it matters:** "Multi-line text" is one of six headline field types, and it is unusable in every reader I tried, including the site's own tools. The person who filled the form thinks they answered; the recipient sees one word.
   - **Where to look:** `qe` → `c.addToPage(r, {...L, font: l})` with no `setFontSize`. Call `setFontSize(0)` (auto) or a fixed 10–11 pt, and maybe expose a font-size field.
   - I rate it P1 because answers are silently lost on paper and in flattened copies. Downgrade to P2 if you prefer.

## P2: where to look

1. **Rotated pages: fields land rotated and in the wrong place.** `rotated.pdf` (/Rotate 90). The field placed at the top-left of the preview (180×22, horizontal) is written as a 140×29 rect in unrotated space, which shows **vertical, at the right edge** (`rot-preview-vs-output`). `qe` uses `getSize()` (unrotated MediaBox) with fractions measured on the rotated preview. Scanned forms often carry /Rotate.
2. **CropBox not at origin: fields shift off the page.** `cropbox.pdf` (CropBox 100,100–512,692). The field placed at 25%/25% comes out at x −80 (half off the visible page) and over the heading, and is 268 pt wide instead of 180 (`crop-preview-vs-output`). Add the CropBox origin and use its size, not the MediaBox's.
3. **Non-Latin answers (Hindi, Cyrillic, CJK, Arabic).**
   - Fields have only Helvetica/WinAnsi in their appearance and no AcroForm `/DR`. In **PDFium (Chrome's viewer)** typed "राम कुमार" and "Москва" render **blank** and the field borders disappear (`pdfium-typed-L01`). pdf.js and MuPDF show them only through their own fallback fonts.
   - A Cyrillic *starting value* makes the build throw `WinAnsi cannot encode "М"`. The user sees **"Couldn't make the fillable PDF. Please try again."** Trying again can never work, and nothing names the script. No use is taken (good).
   - The limitation is written in Details ("characters outside Western European alphabets may not show inside a field"), but the FAQ and headline say the file "fills in any PDF reader", and the site serves hi/ja/zh/ko pages. Fillable Forms already handles "text boxes (any language)", so the font path exists.
   - Suggest: embed a Unicode font in `/DR` (or at least check starting values and say "Starting values can only use Western European letters").
4. **Keyboard-only users can't place a field.** The page area (`fp-page`) has only `onPointerDown`, no tabindex or role, and there are no X/Y inputs; placed fields can be selected with Enter but not moved. Axe can't see this.
5. **Locale pages are English.** All 10 hreflang pages keep the English H1 ("Create Fillable PDF"), title, meta, editor labels and FAQ; only the nav and Quick Buy strip change. Same as #88.

## P3

- **Tab order = placement order.** No `/Tabs` on pages; widget order is creation order (`zip_code` placed first at the bottom comes before `full_name` at the top). pdf.js re-sorts visually; PyMuPDF/pypdf and readers that follow the `/Annots` order don't. Set `/Tabs /R` or sort widgets top-to-bottom.
- **No tooltip / accessible name.** The printed label isn't written to `/TU`, so pdf.js exposes no `aria-label` or title; screen readers get the raw field name.
- **Name handling is silent.** The hint says "Letters, numbers, underscore", but the box accepts anything (only `.` is replaced). `a b c$d` passes validation and is saved as `a_b_cd`. A Hindi name (`नाम`) is listed in the UI but saved as `Field`. Validation checks raw names, so `a b` and `a_b` both pass and the second silently becomes `a_b_2`.
- **Radio defaults make separate groups.** Two radios placed with defaults are named `Group` and `Group_2`, so both can be ticked; each also defaults to the choice "Option 1". The editor does say "name shared buttons the same"; consider defaulting a new radio to the last radio's name.
- **Required on a radio group** comes only from the first radio placed (code: `a.required && c.enableRequired()` runs only when the group is created).
- **Number inputs can't be cleared.** Pages: Backspace on "1" gives "1", then typing 5 gives "15". Width/Height: clearing or typing ≤4 snaps back to the old value.
- **No field validation options** (date/number/email format, max length). Not promised; worth considering for intake forms.
- **Small default targets on phones.** Default checkbox/radio is 16 pt (about 9 px on a 390 px phone preview; a text box is 13 px tall). The tool's own guide lists "checkboxes smaller than a finger can tap" as a common mistake.
- **Non-Latin printed labels aren't searchable.** Hindi/CJK/Arabic labels render but drop out of the text layer (get_text shows " (Hindi label)", "Адрес · ").
- **Cross-links:** Fillable Forms says it "doesn't add form fields to a plain document" but doesn't link here; this page doesn't mention Flatten PDF (the guide does).
- **AcroForm has no `/DR` or `/DA`.** Only per-field DA strings name `/Helvetica`; add `/DR` with the font so readers that regenerate appearances find it.
- **Layout and axe:** iPhone SE overflows by 9 px (a button ends at x=329 on a 320 px screen), ja desktop by 3 px. Axe desktop: `label-content-name-mismatch` + `region` (sitewide). Pixel 7: clean.

## Intent

Someone turning a paper form into one that people can type into needs two things: the fields must land where they put them, and every answer must be readable by whoever receives the file. Placement, field types, Required and the hand-offs are right. Multi-line answers vanish behind a 69 pt font, rotated or cropped scans get fields in the wrong spot, and non-Latin answers go blank in Chrome. The usage gate repeats the shared per-load issue.
